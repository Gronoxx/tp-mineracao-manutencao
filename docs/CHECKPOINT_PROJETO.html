Atualizado: 2026-05-28 Alvo de publicação: MSR Data Showcase Repos: tp-mineracao-manutencao · tp-es2-dataset · tp-es2-anotador Modelo alvo: Stable Code Instruct 3B

Resumo executivo

O projeto tem dupla contribuição: um dataset de pares before→after de refatoração Python e um adaptador LoRA treinado nele. Cinco code smells, três tiers de dados (real minerado, tradução Java→Python, sintético).

Estado atual: 616 pares REAL no Tier A (Gemma-validados, revisão humana pendente) +98 de tradução Java→Python (R1). Os 5 smells cruzam o piso de 42 pares reais — inclusive R2 (53) e R3 (91), que estavam presos, graças à mineração ancorada em rule-ID de linter (ver §3).

A lição central é metodológica: mais importante que os números é como os dados foram obtidos. Mineração cega por palavra-chave rende pouco para smells de critério subjetivo (R2 3%, R3 1,2%); ancorar a busca num rule-ID de linter objetivo (PLR0913/PLR2004/PLR1702) recuperou yields 5–25× maiores. A objetividade do critério não é destino — é uma escolha de como minerar.

Regra de composição (vale para todo o documento): entre 30% e 40% dos dados de treino E de teste de cada smell devem vir do Tier A (real minerado). Tiers B e C preenchem o resto — mas essa regra impõe um piso sobre o dado real e limita quanto sintético cada smell pode absorver (aperta sobretudo R2, com só 23 reais).

O achado científico mais forte já apareceu: o yield de refatorações puras é proporcional à objetividade do critério do smell. Os maiores riscos hoje não são de volume — são validade de label (κ não medido), leakage treino/teste e uma armadilha de contaminação do oracle Sourcery.

1O projeto e a tese

Construir um dataset de pares de refatoração Python (código antes → código depois) para 5 code smells e treinar um adaptador LoRA no Qwen2.5-Coder-1.5B. O paper entrega dataset + modelo — não um sem o outro.

Os três tiers de dados

Tier A — Real Mined base

Commits reais do GitHub minerados via PyDriller (keyword + estrutural), julgados pelo Gemma e validados por detector estático. Deve ser ≥30–40% do treino.

Tier B — Tradução C4 só R1

Pares Java de Extract Method (dataset SWE-Refactor) traduzidos para Python via Qwen-7B. Fecha o gap de R1.

Tier C — Sintético dirigido planejado

O before real de pares APARENTE + sinal AST → after limpo gerado por llama3.1. Obrigatório para R2.

O motivo de existirem três tiers: a mineração sozinha não rende o suficiente para todos os smells. Tiers B e C existem para preencher buracos onde o sinal real é escasso — cada um com um modelo gerador diferente para evitar circularidade (ver §2).

2Arquitetura anti-circularidade

A maior ameaça de validade de um dataset construído com LLM é a circularidade: o mesmo modelo gerar, julgar e ser treinado. A separação de papéis é deliberada e documentada.

PapelModeloJustificativa
Juiz (Tiers A, B, C)gemma4-26b:q3Avalia REAL/APARENTE — nunca gera
Gerador Tier Bqwen2.5-coder:7bTradução Java→Python (tarefa ≠ alvo)
Gerador Tier Cllama3.1:8b≠ Gemma, ≠ Qwen, ≠ StabilityAI
Alvo de treinostable-code-instruct-3bFamília StabilityAI — distinta do juiz e de todos os geradores
Validador (held-out)PyRef + detectores AST + humanoDeterminístico, repos disjuntos — pass/fail independente de LLM

★ Fundamentação acadêmica (padrão a seguir no paper)

A literatura nomeia exatamente os riscos deste desenho e prescreve as mitigações que já adotamos:

  • Self-preference bias (Panickssery et al., NeurIPS 2024): juízes LLM favorecem as próprias saídas e as da mesma família → juiz ≠ gerador ≠ alvo (Gemma · llama · StabilityAI). ✓
  • Avaliação circular/auto-reforçada (“LLM-Evaluation Tropes”, 2025): quando o juiz molda o treino, a métrica deixa de ser informativa, e há contaminação por heurísticas compartilhadas mesmo com times independentes → mitigação prescrita = ground truth humano independente + validador determinístico. ✓
  • Validação estrutural > julgamento de LLM (vários, 2025–26): confiar na estrutura concreta (AST) é mais confiável que a opinião do LLM → por isso o prompt do Tier C usa sinal AST objetivo, não a prosa do Gemma. ✓

Adotado (2026-05-26): a abordagem-padrão acima + checagem cross-family — um segundo modelo, de família distinta do Gemma, valida uma amostra dos pares para descartar viés de juiz único.

Troca do alvo de treino (2026-05-26)

O alvo era qwen2.5-coder:1.5b — mesma família do gerador Tier B (Qwen-7B), abrindo risco de auto-destilação (o pequeno só imitando o irmão maior). Novo alvo: Stable Code Instruct 3B (StabilityAI), família usada em nenhum outro papel do pipeline. Bônus: 2.7B dá mais capacidade para os smells estruturalmente difíceis (R1, R2) e supera o deepseek-1.3b-instruct no Multi-PL (47,2% vs 44,3%). Custos: mais pesado de treinar na GTX 1660 (viável com QLoRA 4-bit + gradient checkpointing) e licença Stability mais condicional (livre para pesquisa; distribuir só o adaptador). Fallback: deepseek-coder-1.3b-instruct (e então remover deepseek-coder-v2:16b da reserva Tier C).

Protocolo de revisão humana — inegociável

100% dos pares de todos os tiers passam por revisão humana cega ao label do Gemma (o revisor vê só before, after e o critério). IAA em ≥50 pares duplo-cego, meta Cohen's κ ≥ 0.61. O κ é a evidência, no paper, de que a definição operacional do Gemma se alinha à humana.

3A história da coleta

A coleta evoluiu em três grandes movimentos: um mine de produção inicial (insuficiente), uma sessão massiva de expansão (10× o volume bruto) e o julgamento por LLM que destilou os pares REAL.

  • 2026-05-19/20 · Mine de produção inicial
    400 pares — todos abaixo do piso da literatura

    36 repos maduros, janela 2020-2024, verificação estrita + permissiva. Em 43 min: 400 pares (258 estritos + 142 parciais). R3 chegou a 64% do mínimo; R1 ficou em 5%. Conclusão: a configuração de produção, sozinha, não dá conta.

  • 2026-05-20 a 22 · Sessão de mineração massiva (Dias 11-12)
    432 → 4.400 pares brutos (10,2×)

    Quatro estratégias de expansão rodadas em sequência (detalhe abaixo). Quality check estático após cada fase: 88,2% CLEAN, 9,8% WARN, 2,0% FAIL.

  • Fase C · cross-file
    ABORTADA — 0 pares em 10h

    Tentou casar funções movidas entre arquivos variando o threshold de similaridade AST {0.5…0.9}. Rendeu zero em todos. Refatorações cross-file reais têm similaridade baixa (~0.3) e ocorrem ao longo de múltiplos commits — o detector atual não as capta.

  • 2026-05-22/24 · Julgamento por LLM
    4.400 brutos → 100% julgados → 436 REAL

    Cada candidato (já filtrado pelo detector estático) passou pelo Gemma-26B-Q3, que classifica REAL vs APARENTE. Aqui apareceu a heterogeneidade brutal de yield entre smells — e a constatação de que mineração cega não bastava para R2/R3.

  • 2026-05-23/25 · Tier B (Caminho C4)
    +98 pares R1 via tradução Java→Python

    350 pares Java de Extract Method (SWE-Refactor) traduzidos por Qwen-7B → filtro estático (NLOC>30 ou CC>10): 47 pares → juiz Gemma (before ≥10L): +51 → 98 pares R1.

  • 2026-05-28 · Mineração ancorada em rule-ID (a virada)
    +180 REAL — R2/R3/R4 cruzam o piso

    Buscar commits que corrigem uma regra de linter pelo rule-ID (ruff PLR0913/PLR2004/PLR1702) → diff via API (sem clonar) → mesmos detectores → Gemma. 672 candidatos, 180 REAL: R2 30/39 (77%), R3 74/382 (19%), R4 13/112 (12%), + bônus R1/R5. Yields 5–25× a mineração cega.

★ Por que o rule-ID funcionou onde a keyword falhou — a lição que importa

A mineração cega rende pouco para R2/R3 porque o critério ("muitos parâmetros", "número mágico") é subjetivo: a palavra-chave captura uma intenção difusa, e o juiz acaba rejeitando quase tudo. O rule-ID de um linter é a objetividade que faltava — um commit que cita PLR2004 resolveu uma violação objetiva e pré-localizada daquela regra. Mesmíssimo pipeline (detector AST + Gemma + revisão humana); só mudou a fonte do candidato, e o yield saltou 5–25×. Conclusão metodológica forte: a baixa minerabilidade de um smell subjetivo não é destino do smell — é da fonte difusa. Troque a fonte por um sinal objetivo e o smell subjetivo vira minerável.

4O que foi encontrado

★ Achado principal — provavelmente o resultado mais forte do paper

A objetividade do critério de um code smell prediz o yield de refatorações puras em mineração por keyword. Com 5 pontos de dado, a correlação é monotônica decrescente (Spearman, 5/5 na ordem esperada): R5 binário (38%) > R1 com threshold (19%) > R4 estrutural-contextual (4%) > R2 (3%) > R3 dependente de domínio (1,2%, n=1.376). O R3 agora tem yield robusto (batch completo, 2026-05-27), não mais estimativa de piloto.

Implicação prática (refinada em 2026-05-28): mineração por keyword é inadequada para smells de critério semântico — mas a solução não é só dado sintético. Ancorar a busca num rule-ID de linter objetivo recuperou o yield (R2 3%→77%, R3 1,2%→19%). Isso torna o achado mais forte: o yield baixo vem da fonte difusa, não do smell em si — troque a fonte por um sinal objetivo e o smell subjetivo vira minerável. Sustenta uma RQ própria, independente dos resultados do LoRA.

Outros achados

  • Refatorações cross-file são indetectáveis com matching estrutural em commit único — ocorrem ao longo de vários commits com similaridade baixa (Fase C, 0 pares em 10h).
  • PR mining: testado e abandonado (piloto empírico, 2026-05-27). O único giant com sinal era o home-assistant (code-quality, 23.186 PRs; airflow/sentry/ray sem label de refac usável). Piloto de 500 PRs atômicos pelo pipeline canônico → 3 candidatos, 0 REAL (disparo 0,6%, ~32 min). O code-quality é dedup de constantes por import, remoção de componentes deprecados, traduções e typing — quase nada casa com os 5 detectores em nível de função. PR-label mining não é fonte viável para estes smells (consistente com os +7 do keyword mining).
  • Tradução Java→Python esbarra no tamanho: métodos Java do SWE-Refactor têm mediana de 19 linhas → em Python ficam curtos demais e não disparam o detector (NLOC>30). Só passam pares cuja origem Java tinha mediana de ~57 linhas.
  • Os 81% de APARENTE de R1 não são só ruído — são um achado: a taxonomia do porquê (multi-objetivo, extração parcial, mudança de assinatura, falso-positivo de keyword) caracteriza a qualidade da mineração por keyword.
  • O piloto superestima o yield: R5 deu 60% no piloto de 50 e 38% no batch completo — a amostra inicial não era representativa. O padrão qualitativo se manteve.

6Maiores riscos atuais

Os riscos que mais ameaçam a aceitação no MSR não são de volume — são de validade. O Data Showcase não rejeita por dataset pequeno; rejeita por label duvidoso, leakage e circularidade.

Papel do Sourcery — validador vs comparador controlado

Decisão: PyRef + detectores são o validador determinístico (pass/fail); Sourcery-AI é só comparador/baseline (o LoRA tem que igualar ou superar). A contaminação só voltaria se o Sourcery fosse, ao mesmo tempo, fonte de treino e comparador — então: não gerar treino com Sourcery. Mesma regra para o PyRef.

Split treino/teste por repositório decidido

Decisão: split por repositório (nenhum repo dos dois lados). Repos de teste a definir e congelar antes de qualquer avaliação; podem ser minerados depois, documentando a qualidade de cada um. Implementação: DataCurator.split() → GroupShuffleSplit. Como a comparação LoRA-vs-baseline é relativa, um eventual desvio de distribuição treino↔teste se cancela.

Validade de label — reporte de κ pendente

Não é falha de desenho: a revisão humana de 100% torna o rótulo humano a verdade do dataset, independente do Gemma. Falta só medir e reportar o IAA (κ entre os dois revisores + κ Gemma×humano) — exigência do MSR, resolvida quando a revisão terminar. Vira risco real só se o κ entre humanos vier baixo (critério ambíguo).

Volume de R2/R3 — custo, não tese médio

Minerar mais R2/R3 não invalida a RQ: se o yield seguir baixo, confirma a tese (e quantifica o custo); se subir, a tese se ajusta. Vencer por volume é legítimo — desde que o critério de REAL não seja afrouxado para inflar o yield (isso sim corromperia tese e dataset). O limite é o custo do juiz (~30s/par). Atalho: R3 tem ~1.325 candidatos minerados ainda não julgados — ~11h de Gemma rende ~26 REAL sem nova mineração.

Circularidade residual do Tier C médio

O gerador (llama) e o juiz (Gemma) ainda se acoplam. Mitigado por usar sinal AST objetivo no prompt — não a prosa do Gemma. Precisa ser explicitado nas ameaças à validade.

Custo do juiz é o teto real médio

Gemma a ~30s/par numa GPU de 6GB. R4 = 1.294 brutos julgados → 52 REAL. Dobrar o bruto ≈ +10h de Gemma para ~50 REAL extras. Volume é limitado pela vazão do juiz, não pela mineração.

Auto-destilação do Tier B resolvido

Antes: gerador (Qwen-7B) e alvo (Qwen-1.5B) eram da mesma família — o pequeno poderia só imitar o irmão maior. Resolvido em 2026-05-26 trocando o alvo para Stable Code Instruct 3B (StabilityAI): sem sobreposição de família com nenhum gerador ou juiz.

CodeBLEU descartado

Decisão 2026-05-26: removido. Penaliza refatoração correta mas diferente do oracle — usar métrica que subestima a própria tese seria tiro no pé. Substituído por preservação de comportamento (execução de testes, eval_execution.py) + checagem de não-introdução de novos smells.

7Sugestões e próximos passos

Prioridades estratégicas

1
Endereçar os blockers reais do MSR antes de volume. κ/IAA (≥0.61 em ≥50 pares duplo-cego) e split por repositório (GroupShuffleSplit). Estes pesam mais na aceitação do que qualquer aumento de volume.
2
Não minerar mais para R2/R3. É incoerente com a tese do paper. Usar Tier C para R2; manter R3 como finding negativo — num Data Showcase, o resultado negativo é uma feature.
3
Se minerar mais, só PR mining ampliado e só para R1/R5. É a única estratégia com headroom não tocado: repos de label disciplinado (home-assistant et al.) que ficaram fora da lista curada. Sinal de intenção humano + filtro documentado = defensável.
4
Firewall do oracle. Qualquer repo que contribua par de treino sai do conjunto held-out (PyRef/Sourcery). Documentar a disjunção explicitamente.
5
Considerar LoRA multi-task com base compartilhada. R1 (182) + R5 (260) sustentam a capacidade geral de refatorar; R2/R3 escassos se beneficiam por transferência. Ataca a escassez no lado do treino, reduzindo a pressão de volume por smell.

⚠ O que NÃO fazer

Não usar PyRef nem Sourcery para minerar dados de treino — ambos são o oracle de avaliação. Não reabrir cross-file com o critério atual (já deu 0 em 10h). Não tratar “mais mineração” como solução para R2/R3.
