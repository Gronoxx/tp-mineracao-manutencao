1. O problema (recapitulação da §4, Desafio 2)

A trava de segurança da §4 precisa distinguir smell real (deve ser refatorado) de smell aparente (parece um smell, mas é código legítimo que não deve ser tocado — validações de segurança em if aninhados, contratos de API estáveis, magic numbers que são códigos de protocolo, etc.).

Uma das duas rotas para isso (Desafio 2) é treinar o classifier diretamente em exemplos negativos: padrões que parecem smell mas devem ser preservados. O obstáculo levantado na §4: esses dados praticamente não existem em forma estruturada e rotulada. Esta nota descreve como pretendemos contornar isso e o que continua sem solução depois.

2. Direção proposta — destilação ancorada

A ideia inicial era gerar os exemplos negativos sinteticamente com um LLM e verificá-los manualmente. Discutida a fundo, ela tem dois furos: (a) o LLM gera a partir do prior dele, não da distribuição real — produz sempre o arquétipo prototípico e deixa regiões inteiras da fronteira de decisão sem cobertura; (b) a verificação manual conserta a precisão dos rótulos, mas não a cobertura do espaço — você não consegue verificar a ausência de algo que não foi gerado.

A direção que adotamos corrige isso ancorando a geração em dados reais:

Destilação ancorada — quatro movimentos

  • Minerar um seed real pequeno de código onde um desenvolvedor real fez o julgamento "isto está ok" (supressões de linter, "won't fix" de ferramentas).
  • Usar o seed real como âncora few-shot da geração sintética — o LLM passa a gerar exemplos que orbitam a distribuição real em vez do prior dele.
  • Revisar manualmente cada exemplo (real minerado e sintético) — re-julgar "é genuinamente não-smell" vs. "é smell apenas suprimido".
  • Reservar um test set 100% real — nunca sintético — para que os números reportados signifiquem algo e para medir o gap sintético→real.

Por que "destilação": um LLM grande que acerta a classificação em parte dos casos pode produzir um conjunto de treino útil, desde que os erros sejam filtrados na revisão. Um classifier pequeno destilado desse conjunto roda barato e offline em produção. O termo "ancorada" marca a correção essencial: a geração é condicionada a exemplos reais, não solta no vácuo.

4. As revisões necessárias

A revisão manual é o que converte rótulos-proxy e exemplos sintéticos em dados de treino confiáveis. Protocolo proposto:

  • Re-julgamento de cada exemplo: para cada item minerado/gerado, um revisor humano decide explicitamente — "isto é genuinamente não-smell" ou "isto é um smell que o dev apenas suprimiu (preguiça, falta de tempo, legado de terceiros, discordância de threshold)". Só a primeira categoria entra como negativo.
  • Revisão dupla + adjudicação em uma amostra: dois revisores independentes, conflitos resolvidos por discussão. Permite medir o kappa entre os nossos próprios revisores — número que deve ir para o relatório.
  • Contexto disponível ao revisor: o revisor enxerga o arquivo/classe ao redor, não só a função isolada.
  • Esforço estimado: algumas centenas de exemplos, revisão dupla com adjudicação — tarefa de dias, não de semanas. É um custo real, mas limitado e orçável (diferente da §4, que temia "inventar a metodologia do zero" — aqui o protocolo já está definido).

5. Como esses dados ajudam o classificador

supressões de linter + SonarQube ──► SEED REAL (revisado) │ ┌────────────────────────────┼────────────────────────────┐ ▼ ▼ ▼ âncora few-shot da treino do classifier TEST SET 100% real geração sintética (seed real + sintético ancorado, (mede F1 honesto + (combate falta de cobertura) ambos revisados) gap sintético→real) │ ▼ exemplos sintéticos ──► revisão manual ──► entram só no TREINO

Os dados cumprem três papéis distintos:

  • Seed real — ancora a distribuição: garante que o classifier veja exemplos da variedade real, escritos por humanos, e não apenas o arquétipo prototípico.
  • Âncora few-shot — a geração sintética condicionada ao seed orbita a distribuição real; ataca diretamente o problema de cobertura da fronteira de decisão.
  • Test set real — torna o F1 reportado significativo e permite quantificar explicitamente o gap sintético→real (se pequeno, a geração funcionou; se grande, isso já é um resultado).

O classifier resultante é um filtro de risco probabilístico de primeiro estágio, barato e offline — não uma garantia. Ele compõe uma defesa em profundidade junto com o teste comportamental do Desafio 1 (verifica preservação de comportamento diretamente) e a aprovação humana de cada diff. Ele não substitui o teste comportamental.

6. Limitações reconhecidas

Conseguir os dados reais torna a abordagem defensável e honesta — remove a objeção de distribuição sintética. Não a torna "resolvida". Os resíduos abaixo sobrevivem a qualquer quantidade de dados e devem ser documentados no relatório (§8 — caveats).

L1 — Rótulo proxy → colapsa no teto de kappa

A revisão manual resolve o descasamento do rótulo proxy (a supressão não é o mesmo que "não é smell"). Mas, ao trocar o proxy por julgamento humano, o erro não desaparece — ele se move para a discordância entre anotadores.

Resíduo: erro irredutível ≈ kappa 0.4–0.6 dos revisores em smells subjetivos. Mitigação: reportar o F1 acompanhado do kappa dos nossos próprios revisores, para separar erro de método de teto irredutível.
L2 — Teto de kappa é propriedade do fenômeno

Cohen's kappa 0.4–0.6 para smells subjetivos é uma propriedade do fenômeno, não dos dados: dois desenvolvedores reais discordam se um dado Long Method é aceitável. Um classifier não ultrapassa o nível de concordância dos rótulos que o treinaram.

Resíduo: F1 capado abaixo de 1 nos smells subjetivos, por construção. Não corrigível.
L3 — A decisão não é function-level (limitação de escopo reconhecida)

Se um padrão é legítimo depende com frequência de contexto fora da função — contrato de API, callers, threat model. O classifier é function-level e não vê esse contexto; o sinal necessário às vezes não está no input. Reconhecido como limitação de escopo do TP.

Resíduo: casos que dependem de contexto cross-function ficam fora do escopo. Vai para §8 como ameaça à validade explícita. Nota: os próprios rótulos da revisão podem codificar contexto que o classifier não consegue reproduzir em inferência.
L4 — Erro correlacionado LLM↔humano

Nos casos genuinamente ambíguos, LLM gerador e revisor humano compartilham priors (o LLM aprendeu de texto humano). A revisão filtra discordâncias, não erros — casos onde ambos erram na mesma direção entram no dataset.

Resíduo: a concordância aparente é inflada pela correlação gerador↔verificador; o F1 reportado é otimista nessa fração. Documentar.
L5 — Gap sintético→real e cross-project

Mesmo ancorada, a geração sintética não reproduz a distribuição real perfeitamente; e F1 cross-project é ~20–30pp menor que within-project.

Resíduo: medir explicitamente o gap sintético→real no test set real e reportar; não eliminável.

Em uma frase: a §4 já dizia que a trava é "mitigada pela aprovação humana, mas não eliminada". Conseguir os dados reais não muda essa frase — torna o primeiro andar (o classifier) viável e honesto, mas o classifier continua sendo um redutor de risco, não uma garantia.
