Manual de Mineração de Pares de Refatoração reprodução consistente

Este guia ensina, passo a passo, como minerar e validar pares de refatoração (antes → depois) exatamente do mesmo jeito que foi feito no projeto. Seguir este manual ao pé da letra é o que garante que os dados produzidos por você e pelos colegas sejam comparáveis e combináveis.

0 · Objetivo & por que consistência importa

O projeto monta um dataset de pares de refatoração em Python para 5 tipos de code smell (R1–R5). Cada par tem o código antes e depois de uma refatoração real extraída do histórico de repositórios maduros. Depois, um LLM local (Gemma 4 26B Q3) julga cada par como real (refatoração legítima) ou aparente (falso positivo).

⚠️ A regra de ouro
Se cada pessoa alterar a janela de tempo, a lista de repositórios, os thresholds dos detectores ou o prompt do Gemma, os dados deixam de ser comparáveis. Tudo neste manual que estiver marcado como NÃO ALTERAR deve ser mantido idêntico.

Os 5 smells

CódigoSmellRefatoração-alvoCritério do detector (canônico)
R1Long MethodExtract Methodnloc > 30 ou complexidade ciclomática > 10 (Lizard)
R2Long Parameter ListIntroduce Parameter Objectnº de parâmetros > 5
R3Magic NumbersReplace with Named Constantliterais sem nome (AST)
R4Deep NestingGuard Clauses / Early Returnprofundidade de aninhamento > 3
R5Dead CodeRemove Dead Codecódigo inalcançável + variáveis não usadas (AST + Vulture)

1 · Visão geral do pipeline

A mineração tem 3 estágios. O detalhe crucial: a palavra-chave na mensagem do commit é só um pré-filtro de velocidade — quem rotula o par é o detector estático, não a mensagem.

┌── Estágio 1 — RECALL ──────────────────────────────────────────────┐ │ Varre commits (janela 2020–2024) cuja mensagem cita refatoração │ │ ("extract method", "guard clause"…). Só um pré-filtro. │ └────────────────────────────────────────────────────────────────────┘ │ ▼ ┌── Estágio 2 — EXTRAÇÃO ─────────────────────────────────────────────┐ │ Para cada função alterada, monta um par candidato (before/after). │ │ Em R1, captura também as funções-helper recém-extraídas. │ └────────────────────────────────────────────────────────────────────┘ │ ▼ ┌── Estágio 3 — VERIFICAÇÃO ──────────────────────────────────────────┐ │ Roda os detectores: aceita o par só se o detector DISPARA no │ │ `before` e NÃO dispara no `after` (ou dispara com magnitude │ │ reduzida ≥10% → marcado `partial=True`). O detector é o rótulo. │ └────────────────────────────────────────────────────────────────────┘ │ ▼ data/raw/<smell>.jsonl (1 arquivo por smell, dedup por id) │ ▼ ┌── VALIDAÇÃO — Gemma 4 26B Q3 ───────────────────────────────────────┐ │ Julga cada par: REAL vs APARENTE + confiança + justificativa. │ └────────────────────────────────────────────────────────────────────┘ │ ▼ ┌── CURADORIA HUMANA (opcional, UI web) ──────────────────────────────┐ │ Revisor confirma/ajusta os pares. │ └────────────────────────────────────────────────────────────────────┘
ℹ️ Por que o corpus é determinístico
O minerador clona cada repositório na hora (via pydriller.Repository), mas só percorre commits dentro da janela 2020-01-01 → 2024-12-31. Como essa janela está no passado, o histórico é imutável: minerar hoje ou daqui a um ano gera o mesmo conjunto de commits — desde que a lista de repositórios e os parâmetros sejam os mesmos.

4 · Configuração imutável NÃO ALTERAR

Toda a configuração da corrida de produção está em extracao/execucao/mineracao.py. Não edite estes valores — eles definem o corpus:

ParâmetroValorO que controla
REPOS36 repositórios madurosfontes da mineração (lista completa no Apêndice B)
SINCE2020-01-01início da janela de commits
TO2024-12-31fim da janela de commits
CAP_POR_SMELLR1 4000 · R2 3500 · R3 1500 · R4 2500 · R5 2000teto de pares por smell (parada, não alvo)
PARTIAL_THRESHOLD0.1aceita refator parcial (redução ≥10% da magnitude)

Os thresholds dos detectores também são canônicos (em detectores/*.py): R1: nloc>30 ou ccn>10 R2: params>5 R4: profundidade>3. Não os altere.

5 · Rodar a mineração

A partir da raiz do repositório (tp-mineracao-manutencao/), com o venv ativo:

python -m extracao.execucao.mineracao

O que acontece:

  • Percorre os 36 repositórios, clonando cada um e varrendo a janela 2020–2024.
  • Escreve data/raw/<smell>.jsonl — um arquivo por smell (long_method, long_param_list, magic_numbers, deep_nesting, dead_code).
  • A escrita é acumulativa e idempotente (dedup por id): rodar de novo não duplica.
  • Um repositório que falhar (clone morto etc.) não derruba a corrida — é registrado e pulado.
ℹ️ Onde a saída cai
Rodando da raiz do repo, os pares vão para tp-mineracao-manutencao/data/raw/. Esse é o diretório que a validação do Gemma vai ler no próximo passo. (No projeto, a cópia oficial do dataset vive no repositório tp-es2-dataset, mantido pelo Gustavo — os pares que você minerar devem bater com os de lá.)
⚠️ A corrida completa é longa
São 36 repositórios grandes — pode levar horas e bastante disco para os clones temporários. Para um teste rápido, edite uma cópia de mineracao.py deixando 1–2 repositórios em REPOS só para validar seu ambiente — mas a corrida oficial usa os 36.

6 · Validação com o Gemma

Com o Ollama rodando e o modelo baixado, valide os pares minerados:

# aponte para o diretório que contém data/raw (aqui, a própria raiz do repo)
python -m extracao.validacao.gemma_judge_dataset --dataset-dir . --smells r1 r2 r3 r4 r5

Comportamento:

  • Para cada par, monta o prompt (Apêndice A) e chama o Gemma com parâmetros fixos: temperature 0.1num_predict 150 num_ctx 6144think=False.
  • Checkpoint incremental: pula pares já avaliados e salva após cada um (resistente a interrupção).
  • Grava em <dataset-dir>/anotacoes/anotacoes_gemma.json.

Faça um ensaio antes da corrida cheia:

# lista os pares pendentes sem chamar o modelo
python -m extracao.validacao.gemma_judge_dataset --dataset-dir . --dry-run --smells r1

# piloto: avalia só 5 pares por smell (mede tempo/qualidade)
python -m extracao.validacao.gemma_judge_dataset --dataset-dir . --pilot 5 --smells r1

Cada anotação no JSON tem o formato:

{
  "veredito": "real",        // real = aprovado · aparente = falso positivo
  "confianca": "alta",      // alta · media · baixa
  "justificativa": "...",    // 1 frase em PT explicando a decisão
  "smell": "R1",
  "ts": "2026-05-23T12:19:28"
}
⛔ Nunca edite o prompt ou os parâmetros
O critério de validação está em PROMPT + SMELL_CONTEXT + os parâmetros do modelo (ver Apêndice A). Alterá-los muda os vereditos e invalida a comparação com o que já foi validado. Se precisar mudar o critério, isso é uma decisão de projeto, não uma escolha individual.

7 · Curadoria humana (UI web)

A revisão manual roda uma interface local em Flask:

python -m extracao.execucao.filtro_smells --data data/raw --reviews data/reviews --port 5050

Abra http://localhost:5050. Para cada par, o revisor vê o diff e marca o veredito (limpa / ruidosa / rejeitar), com justificativa quando exigida. As revisões são salvas separadamente em data/reviews/ — os dados crus em data/raw/ não são modificados.

Apêndice A · Template de validação do Gemma (íntegra)

Fonte versionada: extracao/validacao/gemma_judge_dataset.py. Reproduzido aqui para referência. O placeholder {smell_name}/{smell_rule} é preenchido pelo SMELL_CONTEXT do smell.

Prompt

You are an expert software engineer evaluating refactoring quality.

Smell being checked: {smell_name}
Rule: {smell_rule}

BEFORE:
```python
{before_code}
```

AFTER:
```python
{after_code}
```

Is this a REAL, correct refactoring of the {smell_name} smell?
Answer on the FIRST LINE with exactly one word: REAL or APARENTE (if it is a
false positive, wrong refactoring, or introduces logic changes).
Answer on the SECOND LINE with confidence: alta, media, or baixa.
Answer on the THIRD LINE with a one-sentence justification in Portuguese.

Answer:

Contexto por smell (SMELL_CONTEXT)

Smellsmell_namesmell_rule
R1Extract Method (Long Method)BEFORE deve ser uma função longa/complexa com múltiplas responsabilidades; AFTER deve ficar claramente mais curto, delegando a helpers extraídos, preservando toda a lógica.
R2Introduce Parameter Object (Long Parameter List)BEFORE com parâmetros demais (4+); AFTER agrupa parâmetros relacionados em objeto/dataclass/named tuple, reduzindo a contagem. Lógica preservada.
R3Replace Magic Number/String with Named ConstantBEFORE contém literais sem nome que codificam conhecimento de domínio; AFTER os substitui por constantes nomeadas (ALL_CAPS) significativas, não meros aliases.
R4Replace Nested Conditionals with Guard Clauses (Deep Nesting)BEFORE com condicionais aninhados profundos (3+ níveis); AFTER reduz o aninhamento com early returns/guard clauses, deixando o caminho feliz linear. Lógica idêntica.
R5Remove Dead CodeBEFORE com código inalcançável, variáveis não usadas ou ramos impossíveis; AFTER remove só o código morto, sem stubs/comentários, preservando todo o comportamento alcançável.

Como a resposta é interpretada (parsing)

LinhaConteúdoMapeamento
1ªREAL ou APARENTEveredito = real / aparente (default aparente se ambíguo)
2ªalta / media / baixaconfianca (default media)
3ª+frase em portuguêsjustificativa

Parâmetros do modelo (fixos)

MODEL       = "batiai/gemma4-26b:q3"
TEMPERATURE = 0.1
NUM_PREDICT = 150
NUM_CTX     = 6144
think       = False
