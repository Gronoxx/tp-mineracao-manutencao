Pipeline: AST decomposição → 9 detectores estáticos → 5 LoRAs de refatoração (quando aplicável) → loop iterativo até clean → árvore hierárquica → aprovação manual de diffs.

2. Future Work 1 — diferido por escopo/complexidade (independente de prazo)

O que está aqui e por quê

Itens que o trio decidiu deixar de fora antes da pressão do prazo, por motivo de complexidade, ambiguidade na literatura ou por ser projeto separado por si só. Mesmo com 11 semanas, esses provavelmente ficariam de fora.

2.1 Workarounds de smells multi-função e baseados em histórico (Camada 4 original)

  • Type-4 semantic clones — viável com UniXcoder + GPTCloneBench Python pairs, mas é um detector adicional com infra e avaliação próprias (~1.5 sem)
  • Shotgun Surgery — exigiria flag --repo-path + mineração de histórico de commits via PyDriller (~2 sem)
  • Divergent Change — compartilharia infra com Shotgun, mas adiciona 1 smell a mais (~1 sem)

2.2 Trava de segurança via geração automática de testes

Camada que distinguiria "smell real que deve ser refatorado" de "smell aparente mas necessário no contexto" (e.g., if aninhados em validações de segurança, magic numbers que são códigos HTTP).

O trio reconheceu dois desafios independentes que tornam isso um projeto à parte:

  • Desafio 1: Geração automática de testes Python que verifiquem comportamento (não apenas exercitem código) é área de pesquisa ativa — Pynguin foi tese de doutorado, LLM-based test generation ainda é open research. Provavelmente exigiria outro LoRA dedicado, com seu próprio dataset, treinamento e avaliação. Spin-off potencial: a geração de testes pode virar feature paralela de valor — "bateria de testes auto-gerados para código legado".
  • Desafio 2: Treinar o classifier diretamente em exemplos negativos ("parece smell mas é necessário") exige dados que praticamente não existem em forma estruturada — fontes potenciais (PR reviews "leave as is", # pylint: disable justificados, "won't fix" do SonarQube) são esparsas e contextualmente ambíguas. Catalogar é projeto de pesquisa empírica em si.

2.3 Mira em publicação pós-TP

Submissão a workshop acadêmico (MSR Student Track 2027, ICSE-SRC, ESEM Short Paper) após a entrega do TP. Decisão revisitada se o trio quiser estender o trabalho depois.

3. Future Work 2 — diferido por prazo de 22/06

O que está aqui e por quê

Itens que estavam no escopo até semanas atrás mas saíram porque o prazo de 6.5 semanas (07/05 a 22/06) não comporta a ambição original. Se o TP tivesse 11 semanas como planejado inicialmente, esses itens entrariam.

3.1 Detecção ML (Camada 3 inteira)

Os 4 LoRAs classificadores treinados para detectar smells onde a literatura mostra gap ML > regras:

  • Long Method classifier (LoRA C1) — Beyazit 2026: ML F1 0.87 vs. regras 0.84, gap +3pp
  • Feature Envy classifier (LoRA C2) — gap +8pp
  • God Class classifier (LoRA C3) — gap +23-28pp
  • Data Class classifier (LoRA C4) — gap +11pp

Long Method volta a usar regras estáticas (Lizard + Pylint) no escopo atual. Os outros 3 smells ML (Feature Envy, God Class, Data Class) saem do escopo de detecção também — não serão detectados pela ferramenta no TP.

3.2 LoRAs de refatoração de smells class-scope

  • R6 Move Method (refatoração de Feature Envy) — exigiria detecção de Feature Envy, que saiu do escopo
  • R7 Extract Class (refatoração de God Class) — exigiria detecção de God Class, que saiu do escopo

3.3 Ablação científica rules vs. ML para Long Method

Tabela comparativa no paper que mostraria F1 das regras (Lizard+Pylint) vs. F1 do classifier ML (LoRA C1) para Long Method, demonstrando que o gap é apenas +3pp em condições honestas. Sem o classifier C1 treinado, essa ablação não é possível.

Total cortado pelo prazo: 4 LoRAs classificadores (C1-C4) + 2 LoRAs de refatoração (R6, R7) + 3 smells ML adicionais (Feature Envy, God Class, Data Class) + ablação Long Method. O paper documenta tudo isso como direção futura concreta, com referência aos achados de literatura que justificam.

4. Divisão das trilhas

Cada trilha tem ~85-95 horas de trabalho estimado, com mistura de tarefas técnicas e operacionais. Self-assignment livre — cada um escolhe a trilha que combina mais com seu background.

Sugestão de afinidade

  • Trilha A: quem é mais sólido em Python AST e ferramentas de análise estática
  • Trilha B: quem tem mais background ML e quer mexer com fine-tuning
  • Trilha C: quem escreve melhor (vai pegar o relatório) e gosta de integração de sistemas
Trilha A — Mineração + Detecção Estática ~85 horas

P1 — Crítico

  • P1 AST decomposition utility — biblioteca que particiona arquivos Python em funções/métodos/classes ~10h · sem 1
  • P1 PyDriller mining pipeline — extração de pares (antes, depois) de commits de refatoração em ~15-20 repos Python ~25h · sem 1-2
  • P1 5 detectores Camada 1 — Long Method, Long Param List, Magic Numbers, Deep Nesting, Dead Code (wrappers sobre Lizard, Pylint, ruff, vulture) ~25h · sem 2-3

P2 — Importante

  • P2 4 detectores Camada 2 — Refused Bequest (MRO), Duplicate (NiCad ou AST hash), Long Message Chain (PyExamine port), Middle Man (PyExamine port) ~25h · sem 3-4
  • P2 AST diff validator — confirmar que pares minerados batem com o tipo de mudança alegado pelo commit; descarta pares ruins do dataset ~10h · sem 2

P3 — Desejável

  • P3 Refinamento de regras — calibrar thresholds, tratar edge cases (decoradores, async, comprehensions) ~5-10h · sem 5
Dependências de saída: AST utility entrega na sem 1 (desbloqueia C); primeiro batch minerado na sem 2 (desbloqueia B); 5 detectores Camada 1 na sem 3 (desbloqueia integração C).
Trilha B — Treino e Avaliação dos LoRAs ~90 horas

P1 — Crítico

  • P1 Setup HuggingFace + PEFT pipeline — código de fine-tuning supervisionado para Qwen2.5-Coder-1.5B com adaptadores LoRA ~15h · sem 1
  • P1 Curadoria do primeiro dataset (Long Method) — filtrar e validar pares minerados pela Trilha A para R1 ~10h · sem 2
  • P1 Treino R1 (Long Method → Extract Method) — primeira prova de conceito; valida que pipeline funciona ~10h · sem 3
  • P1 Treino R2 e R3 — Long Param List → Parameter Object; Magic Numbers → Named Constant ~15h · sem 3-4

P2 — Importante

  • P2 Treino R4 e R5 — Deep Nesting → Guard Clauses; Dead Code → Remove ~15h · sem 4-5
  • P2 Avaliação execution-based dos 5 LoRAs — rodar testes do projeto-alvo antes/depois da refatoração; reportar % de testes que continuam passando ~15h · sem 5
  • P2 Curadoria dos datasets restantes (R2-R5) ~15h · sem 3-4

P3 — Desejável

  • P3 Hyperparameter tuning — variar rank, alpha, lr nos LoRAs; reportar melhor configuração ~8h · sem 5
  • P3 B1 multitask LoRA — treinar um LoRA único nos 5 smells juntos (baseline para o paper) ~5h · sem 5
Dependências de entrada: precisa do batch minerado da Trilha A (sem 2). Dependências de saída: R1 funcionando até sem 3 (desbloqueia integração C); 5 LoRAs até sem 5 (necessário para avaliação final).
Trilha C — CLI, Integração e Relatório ~95 horas

P1 — Crítico

  • P1 CLI esqueleto + estrutura do repo — Typer com comando detect, estrutura de pastas, pyproject.toml ~12h · sem 1
  • P1 Pipeline iterativo de detecção — orquestra AST decomposition (de A) → 9 detectores → loop até clean com critérios de parada (max-iter K=5, oscilação) ~20h · sem 2-3
  • P1 Integração detectores → LoRAs → diffs — chamar LoRA correto para cada smell flagueado, gerar diff, apresentar ao usuário ~18h · sem 4
  • P1 Relatório paper-style — 4-6 páginas formato ACM/IEEE, com motivação, RQs, metodologia, resultados, discussão, ameaças à validade, future work (separado FW1 vs FW2) ~25h · sem 6-7

P2 — Importante

  • P2 Held-out fixtures (~40 funções) — coletar/escrever amostras Python rotuladas pelo trio para avaliação de detecção ~12h · sem 5
  • P2 Baselines B0 e B3 — B0: LLM zero-shot Llama-3.1 / Qwen-Coder com prompt; B3: Rope mecânico para refatorações que ele suporta ~18h · sem 5
  • P2 Output em árvore com Rich — visualização hierárquica da estrutura do código com smells anotados ~10h · sem 4

P3 — Desejável

  • P3 Replication package — Dockerfile + make all que reproduz tabelas e figuras do relatório ~10h · sem 7
  • P3 Demo gravado — vídeo curto (3-5 min) mostrando uso da CLI em arquivo Python real ~5h · sem 7
Dependências de entrada: AST utility (sem 1 de A), 5 detectores Camada 1 (sem 3 de A), R1 funcionando (sem 3 de B). Trilha C tem maior diversidade de tarefas e a maior responsabilidade pelo relatório final — quem pegar essa trilha será o ponto focal de integração nas semanas 6-7.
