1. O que mudou desde a primeira proposta

Resumo das mudanças propostas

  • De 5 smells intra-função para 12 smells em três camadas — investigação da literatura mostrou que a maioria dos smells reconhecidos pode ser detectada via regras estáticas com F1 competitivo, e que ML é justificado para um subset específico.
  • Long Method passou a ser detectado via ML (LoRA classifier sobre Qwen2.5-Coder-1.5B), com regras estáticas mantidas em paralelo apenas como ablação no paper. Justificativa: os dados de mineração que usaremos para treinar o LoRA de geração (Extract Method) servem simultaneamente para treinar o classifier — custo zero adicional de dados. F1 esperado em Python ~0.65-0.80 (contra ~0.84 das regras em Java cross-project; transferência cross-language perde algo).
  • God Class, Feature Envy, Data Class entram com detecção ML — literatura recente (Beyazit 2026, Liu 2018/2023, Kovačević 2022) confirma gaps de +8 a +28pp.
  • Stack ML unificado: Qwen2.5-Coder-1.5B é o único modelo base; 11 adaptadores LoRA são swapados conforme a tarefa (refatoração ou classificação).
  • Detecção 100% offline — sem APIs externas. Todo modelo roda local com pesos baixados.
  • Workarounds opcionais identificados para 3 smells antes "fora do escopo" (Type-4 clones, Shotgun Surgery, Divergent Change). Decisão pendente do trio — detalhamento de esforço por smell na §6.
  • Trava de segurança via geração automática de testes — gap identificado pelo grupo: nem todo código que parece um smell deve ser refatorado (e.g., `if` aninhados em validações de segurança). Direção proposta detalhada em §4. Status: em desenvolvimento, sem solução final ainda.

3. Arquitetura unificada

arquivo.py ↓ AST decomposição (ast stdlib, determinístico) │ ├── funções/métodos │ ├── 4 detectores estáticos camada 1 (Long Param, Magic, Deep Nest, Dead Code) │ ├── Long Method via Qwen + LoRA classifier (camada 3) │ │ └── regras Lizard+Pylint computadas em paralelo (ablação no paper) │ │ │ └── (sobre métodos com contexto da classe owner) │ Feature Envy via Qwen + LoRA classifier (camada 3) │ ├── classes (com lista de métodos e atributos) │ ├── 4 detectores estáticos camada 2 (Refused Bequest, Duplicate, Long Chain, Middle Man) │ └── Qwen2.5-Coder-1.5B + LoRA classifier (God Class, Data Class) │ └── multilabel sigmoid sobre embedding da classe │ └── (opcional, se workarounds aprovados) ├── pares de classes → UniXcoder embedding similarity (Type-4 clones) └── repo + histórico → PyDriller co-change (Shotgun, Divergent)

Stack ML unificado — 11 LoRAs sobre o mesmo modelo base:

  • 7 LoRAs de refatoração (R1-R7): Long Method (Extract Method), Long Param List (Introduce Parameter Object), Magic Numbers (Replace with Named Constant), Deep Nesting (Guard Clauses), Dead Code (Remove), Feature Envy (Move Method), God Class (Extract Class)
  • 4 LoRAs de classificação (C1-C4): Long Method, Feature Envy, God Class, Data Class — todos em produção

Cada LoRA pesa 5-50 MB, treina em 1-3h em GPU gratuita (Colab/Kaggle), e é swapado em runtime sem recarregar o modelo base.

Reuso pleno do dataset minerado:

  • PyDriller extrai pares (antes_smelly, depois_clean) de commits de refatoração
  • Para LoRAs de refatoração: par completo é input/output
  • Para LoRAs de classificação: a função/classe "antes" + label do tipo do commit
  • Mesma mineração serve aos dois conjuntos de LoRAs — sem custo duplicado de aquisição de dados. Esse é precisamente o motivo de Long Method ir para ML: já vamos minerar pares de Extract Method para o LoRA R1, então temos dados grátis para o LoRA classifier C1.

4. Trava de segurança: distinguir smell real de smell aparente

O grupo identificou um gap importante: nem todo código que parece um smell é realmente um problema. Refatorar agressivamente nesses casos pode quebrar comportamento crítico. Casos comuns:

  • if aninhados profundos em funções de validação de segurança, onde cada camada confirma uma pré-condição crítica antes da próxima (autorização → autenticação → input sanitization → execução)
  • "Long Method" que é sequência linear de transformações sem alternativas razoáveis (parsers, pipelines de ETL, máquinas de estado)
  • "Magic Numbers" que são códigos de protocolo bem conhecidos (HTTP 200/404, bytes hex, RFC constants) cuja substituição por nome adicionaria ruído sem clareza
  • "Dead Code" aparente em branches dependentes de input runtime não capturado por análise estática (e.g., if config.experimental_feature:)
  • Funções com muitos parâmetros que correspondem a contratos de API estáveis cuja mudança quebraria callers externos

A ferramenta precisa diferenciar dois cenários:

  • Smells reais que devem ser refatorados → gerar diff, propor mudança ao usuário
  • Padrões que parecem smells mas devem ser preservados → não propor refatoração, ou propor com aviso explícito

Direção proposta (em desenvolvimento)

Aproveitando que nosso escopo é function-level, a ideia é:

  1. Para cada função-alvo identificada como candidata a refatoração, gerar automaticamente um conjunto de testes que captura o comportamento da versão original
  2. Aplicar a refatoração proposta pelo LoRA correspondente, gerando a versão modificada
  3. Executar os testes auto-gerados em ambas as versões (original e refatorada)
  4. Se os testes na versão refatorada falharem ou divergirem do comportamento original, rejeitar a refatoração automaticamente e marcar o smell como "provável falso positivo — comportamento crítico não preservável"
  5. Se os testes passarem em ambas as versões, apresentar o diff ao usuário para aprovação manual (fluxo normal)

Essa trava serve a dois propósitos simultâneos:

  • Garantia de preservação de comportamento (test-and-roll-back automático antes de mostrar qualquer diff)
  • Sinal pedagógico ao usuário: o output da CLI inclui uma seção "refatorações rejeitadas pela trava" indicando candidatos que parecem smells mas que provavelmente são intencionais

Status: gap identificado, solução final pendente

Decisões abertas que o trio precisa enfrentar quando essa camada for implementada:

  • Qual mecanismo de geração automática de testes? Candidatos: Pynguin (search-based test generation para Python), Hypothesis (property-based testing), geração via LLM (usando o próprio Qwen-Coder), ou combinação dos três
  • Cobertura mínima aceitável para considerar a trava confiável (80% de branches? 95%? cobertura mutacional?)
  • Tratamento de funções com I/O ou estado externo (banco, rede, filesystem) — auto-mock? skip? marcar como "trava não aplicável"?
  • Custo computacional adicional — geração + execução pode dobrar o tempo de inferência da CLI; quanto é aceitável?
  • Apresentação ao usuário — como diferenciar visualmente "smell rejeitado pela trava" de "smell não detectado" no output em árvore?

Por que essa camada pode virar outro projeto inteiro

Reconhecemos honestamente que a trava de segurança tem complexidade comparável ao escopo principal do TP. Dois desafios independentes, qualquer um deles capaz de absorver semanas de trabalho:

Desafio 1 — Gerar testes que verificam comportamento, não só exercitem código.

  • Geração automática de testes Python é área de pesquisa ativa. Pynguin foi tese de doutorado; LLM-based test generation (TestPilot, CodaMosa, papers recentes do MIT 2024-25) ainda é open research.
  • Se quisermos qualidade que justifique a trava, provavelmente precisamos de outro LoRA dedicado à geração de testes — outro treinamento, outro dataset minerado (pares (função, suíte de testes válida)), outras métricas de avaliação (mutation score? branch coverage? equivalência funcional?). Isso por si só é projeto de complexidade similar ao nosso.
  • Bônus arquitetural: se conseguirmos boa geração de testes, o output pode ser oferecido ao usuário como feature paralela — "bateria de testes auto-gerados para seu código legado". Tem valor real para devs que herdam projetos sem cobertura, mas reforça que estamos falando de mini-projeto à parte com escopo próprio.

Desafio 2 — Onde estão os dados de "parece smell mas não é"?

  • Alternativa ao Desafio 1: em vez de filtrar comportamentalmente via testes, treinar o classifier diretamente em exemplos negativos (padrões que parecem smell mas devem ser preservados — validações de segurança, contratos de API, códigos de protocolo).
  • O problema: esses dados praticamente não existem em forma estruturada. Fontes potenciais — todas problemáticas:
    • PR reviews com "leave as is": existe, mas dispersa, exige mineração + classificação de comentários em texto livre
    • # pylint: disable com justificativa: raramente é justificado, e a justificativa (quando existe) é texto não-rotulado
    • Marcações "won't fix" do SonarQube: existem em projetos com SonarQube ativo, mas a base privada da maioria dos repos não expõe esses dados publicamente
    • MLCQ dataset: tem labels "none/minor/major/critical" — label "none" pode significar "não-smelly" OU "smelly mas aceitável no contexto", sem distinguir os dois
  • Catalogar e rotular sistematicamente esses dados é um projeto de pesquisa empírica em si — do tipo que dá um paper inteiro só com a metodologia de coleta.

Implicação prática para nosso TP:

  • Muito provavelmente a trava completa fica como trabalho futuro documentado, com prova-de-conceito limitada se o tempo permitir.
  • O paper reconhecerá honestamente que sem essa camada, refatorações sugeridas podem propor mudanças que quebram comportamento legítimo (mitigado pela aprovação humana de cada diff, mas não eliminado).
  • Se o trio decidir abraçar parte do Desafio 1 dentro do TP, precisamos cortar escopo em outro lugar (provavelmente os workarounds da camada 4 saem) — não dá para fazer tudo em 11 semanas.

Cronograma: esta camada será implementada após a pipeline base de detecção+refatoração estar estável (após semana 8). Se o tempo ficar curto antes da entrega, vira trabalho futuro documentado no paper como ameaça à validade reconhecida. Reconhecer o gap honestamente vale mais que omitir.

8. Caveats honestos (a documentar no paper)

  • Quase toda evidência ML é Java. Para Python, transferência perde ~5-10pp em F1. Documentamos como limitação.
  • Smells "estruturais" não têm F1 contra ground truth humano em Python. Adotamos via determinismo AST/CFG; reconhecemos a ausência de teste empírico direto.
  • Cohen's kappa entre anotadores é 0.4-0.6 para smells subjetivos — teto que nenhum método cruza.
  • Cross-project F1 é ~20-30pp menor que within-project. Os números acima são cross-project (mais honestos).
  • Refatoração inter-classe (Move Method, Extract Class) é categoricamente mais difícil que intra-função. Risco de qualidade subjetiva inferior aceito como trade-off pela cobertura ampliada.
  • Long Method em Python via ML é uma escolha pragmática, não comprovada empiricamente como superior a regras (cuja diferença é só 3pp em Java cross-project). A justificativa principal é o reuso de dados — a literatura per se não recomenda preferencialmente ML para esse smell.
  • Sem trava de segurança (caso ela não seja implementada a tempo), refatorações sugeridas podem propor mudanças que quebram comportamento legítimo (validações de segurança, contratos de API, magic numbers que são códigos de protocolo). Isso é uma ameaça à validade reconhecida da ferramenta, mitigada pela aprovação humana de cada diff mas não eliminada (usuário pode aprovar sem perceber a quebra). A §4 detalha a direção proposta para fechar esse gap.
